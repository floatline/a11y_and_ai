# A11y & AI — план подготовки интерактивного стенда

**Репозиторий:** https://github.com/MefistAldemisov/a11y_and_ai  
**Плановая демонстрация:** 19 ноября 2026 года  
**Стек:** React 19, TypeScript, Vite, Gravity UI, Playwright  
**Статус:** план работ, а не отчёт о реализованных функциях или проведённых тестах  
**Формат:** короткие самостоятельные или сопровождаемые эксперименты на десктопе и телефоне

## 0. Цель и ограничения

Посетитель выполняет простую задачу в ToDo в **Hard Mode** (ориентир — **3–4 минуты**), сталкивается с намеренно внедрёнными барьерами доступности, после чего ведущий или сам посетитель переключает интерфейс в **Easy / Original Mode** и повторяет ту же задачу. На мобильном устройстве — аналогичная последовательность. Результат — наглядный контраст поведения, а не задача «найти и исправить баги».

**Не делаем:** полный WCAG-аудит и исправление исходного приложения, систему баллов, пользовательские аккаунты, телеметрию посетителей, разработку собственного скринридера, тяжёлую архитектуру плагинов.

**Термины:**
- `Original` — исходное поведение репозитория **без дополнительных намеренных поломок**; **не** утверждение о полной доступности.
- `Hard` — исходное приложение + выбранные искусственные поломки.
- `Solo` — самостоятельно запускаемая последовательность «инструкция → попытка → сравнение».
- `Visual simulation` — условная иллюстрация отдельных нарушений восприятия; не реконструкция реального опыта человека с диагнозом.

**Обязательные требования стенда:**
1. Одна видимая кнопка **«Сбросить демонстрацию»** для ведущего, не затрагиваемая намеренными поломками.
2. Все кейсы воспроизводимы и имеют заранее подготовленные данные.
3. Никакие переключатели не должны вызывать неустранимую блокировку устройства/страницы.
4. Основные сценарии работают на реальном смартфоне, а не только при эмуляции viewport в DevTools.
5. На телефоне QR-код открывает реально доступный с телефона URL Егора, **не** `localhost` ноутбука.

### 0.1. Подтверждённая конфигурация стенда (16 ноября)

**Физически:** два независимых ноутбука — **Windows** и **Mac**; **по одной паре наушников для каждого**. На столе/стойке — **два QR-кода для iPhone и Android**. Веб-приложение размещается **на хосте Егора**, а не на `localhost` ноутбуков. Посетители открывают его на собственных телефонах.

| Точка | Связка | Основной опыт | Ресурсы |
|---|---|---|---|
| **Windows-станция** (позже, решено 16.11: сначала Mac + VoiceOver) | Chrome + NVDA | Клавиатура, имена/иконки, `flex-reverse` против DOM-порядка, focus outline, модалки | Ноутбук, клавиатура, отдельные наушники; NVDA и его голос заранее настроены |
| **Mac-станция** | Safari + VoiceOver | Вложенность/SVG, виртуальная навигация, фокус и модалки, сравнение с Windows | Mac, отдельные наушники; VoiceOver и настройки клавиатурной навигации Safari проверены |
| **QR iPhone** | Safari + опционально VoiceOver | Сенсорное прохождение Hard → Original; VoiceOver для желающих и тестов | Собственный телефон посетителя, публичный HTTPS URL |
| **QR Android** | Chrome + опционально TalkBack | Аналогичный touch-сценарий; TalkBack для желающих и тестов | Собственный телефон посетителя, публичный HTTPS URL |

**Организация двух станций:** обе работают параллельно и **не делят localStorage**. На каждой — собственный reset и seed-данные. Браузерные URL могут совпадать; не требуется backend для синхронизации состояния, хранить ввод пользователей на сервере не нужно. При необходимости ведущий демонстрирует один и тот же сценарий на двух скринридерах.

**Два QR ≠ два разных приложения.** Желательно один `dist/` и один origin с различающимися query-параметрами, например `?demo=1&platform=ios` и `?demo=1&platform=android`; оба адреса ведут в тот же сценарий, но с разными короткими инструкциями по жестам. Детект платформы **не должен** автоматически менять набор ошибок и быть условием работоспособности. При нехватке времени два QR могут вести на один URL, а инструкции печатаются рядом.

**Наушники:** до открытия проверить маршрутизацию аудио по отдельности (скринридер Windows → наушники Windows; VoiceOver Mac → наушники Mac), громкость, возможность быстро включить/отключить скринридер и вернуть управление. Подключение проводное предпочтительно для предсказуемости; Bluetooth допустим после реального прогона. Для мобильных гостей **наушники не заявлены** — нельзя строить обязательный мобильный сценарий на приватном прослушивании TalkBack/VoiceOver.

**Безопасность:** ведущему нужен способ остановить попытку или эффект, не зависящий от focus trap и скринридера. Включать TalkBack/VoiceOver на личном телефоне участника только с его согласия и объяснением, как отключить. При появлении очереди мобильные QR должны вести к самодостаточной инструкции, а не требовать одновременного участия ведущего.

## 1. Путь посетителя: один основной сценарий

### 1.1. Desktop, 3–4 минуты Hard + сравнение

1. **Старт (15–20 с):** экран со стартовой задачей, короткой инструкцией и кнопкой «Начать». Выбирается один из предзаданных кейсов, данные сбрасываются.
2. **Hard (до 3–4 мин):** найти чеклист `Конференция`, раскрыть его, создать задачу `Проверить презентацию`, выставить критический приоритет и отметить её выполненной. Для краткой версии достаточно 2 из этих действий.
3. **Способ управления:** по умолчанию клавиатура; для сценария незрячего использования — настоящий NVDA/VoiceOver, возможность выполнять с закрытыми глазами или с непрозрачным визуальным слоем. Это **не** медицинская симуляция слепоты.
4. **Таймер:** показывает прошедшее время, не обрывает взаимодействие автоматически; ведущий может завершить попытку раньше. Без оценивания скорости как «способностей» человека.
5. **Сравнение (30–60 с):** кнопка `Переключить в Original`; данные возвращаются к **тому же исходному состоянию**, таймер сравнения запускается заново. Контраст следует объяснить в 1–2 фразах.
6. **Завершение:** краткое «Что мешало» (например, неверное имя кнопки, порядок фокуса, фокус вне диалога), затем **сброс**.

### 1.2. Mobile

- На стойке два QR: «iPhone / Safari» и «Android / Chrome»; оба открывают один деплой на хосте Егора. При желании query-параметр позволяет показать нужную короткую инструкцию.
- Повторяется та же пара Hard → Original с идентичными данными.
- Для проверки доступности — **TalkBack + Chrome на Android** и **VoiceOver + Safari на iPhone**. На личном телефоне посетителя эти функции могут быть выключены: визуальный/touch-сценарий должен работать без них, а озвучивание — быть опциональным этапом с согласием и инструкцией.
- Для зрительных кейсов — касания, масштабирование и визуальный поиск элементов; для остальных — голосовые подсказки инструктора, если скринридер непривычен.
- Кнопки `Сброс`, `Остановить эффект`, `Выйти` остаются доступными с клавиатуры, касанием и вспомогательными технологиями.

### 1.2.1. Форматы и кейсы

> Статус: решено 16.11 (раунды 5–6). Все пять кейсов — P0, посетитель выбирает любой. Windows + NVDA — так же, как Mac + VoiceOver, проверяется вторым. Итоговый объём — раздел 4.1. Отдельных режимов «Зрение» и «Клавиатура» **нет**: управление всегда с клавиатуры, а фильтры зрения (VISION-01/02, FX-01) из плана убраны. Мобилка — часть Solo. NVDA — позже, сначала Mac + VoiceOver. **Приоритет: Solo и пара, оба на клавиатуре.** «Опасное удаление» (2Б) — в самом конце очереди.

**Два формата (раздел 1.3):**
- **Solo** — посетитель один. Вариант **«пустой экран»**: поверхность приложения не видна совсем, остаётся только звук скринридера.
- **В паре** — ведомый не видит экран и управляет с клавиатуры, штурман видит и помогает только голосом.

Кейсы одинаковы для обоих форматов; отличается только текст задания. Кейс описывается одной записью: название, задание, шаги с условием «выполнено», seed. **Половина кейсов — наш ToDo с другим seed и заданием**, без нового интерфейса.

| Кейс | Задание | Ловушка в Hard | «Ага» | UI |
|---|---|---|---|---|
| **1Б** | Отметь выполненной задачу «Позвонить спикеру» | чекбоксы без имён («флажок, флажок»); `reverseOrder`: визуально третья задача при чтении первая | отмечает **не ту** задачу; в паре штурман видит ошибку, а ведомый нет | ToDo |
| **2В** | Отметь доклад в 14:00 | расписание = задачи «10:00 …», «12:00 …»; на экране по времени, при `Tab` в обратном порядке; outline выключен | отмечает доклад в 16:00; в паре штурман тоже не видит, где фокус | ToDo |
| **2А** | Зарегистрируйся | у полей только placeholder; DOM перемешан (`Tab`: Пароль → Имя → Отправить → Email); autofocus на втором поле; «Условия» в модалке без ловушки | печатает имя в поле пароля | Регистрация (новый) |
| **1А** | Купи 2 билета «Стандарт», убери VIP | `−`/`+`/корзина звучат «кнопка»; у SVG мусорный `title`; карточка кликабельна целиком, внутри кнопка (BREAK-04) | в Original: «Увеличить количество: Стандарт, сейчас 1» | Корзина (новый) |
| **2Б** | Удали одну задачу, но не чеклист | фокус остаётся на «Удалить чеклист» за модалкой; Enter удаляет всё | реальный ущерб от фокуса вне диалога | ToDo + диалог. **В самом конце очереди** |

**На телефоне (Solo):** те же кейсы; управление касанием или подключённой клавиатурой.

**Убрано:** режимы «Зрение» (3А, 3Б) и отдельный «Мобильный» (4А, 4Б). **Отложено:** К4 «Профиль» с `alt` (BREAK-05), `silentErrors`.

### 1.3. Режимы показа

| Режим | Для кого | Что происходит |
|---|---|---|
| **Guided** | Ведущий с участником | Ведущий включает/выключает отдельные поломки, демонстрирует разницу |
| **Solo** | Посетитель сам | Три экрана: инструкция → попытка с таймером → сравнение и краткое объяснение |
| **В паре** | Двое посетителей | **Ведомый** не видит экран и управляет с клавиатуры (VoiceOver); **штурман** видит экран и помогает только голосом, руками не трогает. Те же кейсы, таймер и шаги, что в Solo; отличается только текст задания с ролями |
| **Free Play** | Разработчики на стенде | Каталог независимых переключателей, можно комбинировать эффекты |

**MVP:** Guided + короткий Solo. Free Play — тот же набор переключателей в панели, без сложного «движка».

**Что даёт пара (почему это интересно):**
- штурман говорит языком картинки («нажми карандаш справа»), а ведомый слышит «кнопка». В Hard у них нет общего языка, в Original штурман видит те же слова, что звучат;
- без outline **даже зрячий штурман** не видит, где фокус. Теряются оба.

**Без своего кода, средствами ОС:**
- Что слышит ведомый, штурман читает в панели субтитров: на Mac — **VoiceOver Caption Panel**, на Windows (позже) — **NVDA Speech Viewer**.
- «Пустой экран» в Solo: либо своя чёрная поверхность в приложении, либо **Screen Curtain** скринридера (вопрос раунда 6).
- Пара на ноутбуке: маска для сна для ведомого. Её нужно положить на стенд.

## 3. Конкретная реализация переключаемых дефектов

### BREAK-01 / BREAK-04. Вложенность, SVG, иконки, названия

**Сценарий:** пользователь видит знакомые `+`, карандаш, корзину, стрелку раскрытия, но скринридер не сообщает их назначение или сообщает мусор/неверное имя.

**Где:** `src/components/ChecklistCard/ChecklistCard.tsx`, `src/components/TaskItem/TaskItem.tsx`, при желании отдельный `src/demo/components/NestedControlsTrap.tsx`.

**Реализация:**
- Переключатель `iconsWithoutNames`: убрать `aria-label` только у кнопок с одним SVG; не полагаться на то, что сам `<Icon>` обязательно получит доступное имя — проверить итоговый accessibility tree.
- `misleadingSvgNames`: для одной кнопки использовать неверное доступное имя (`Удалить` вместо `Редактировать`) либо вложенный SVG с `<title>`-подобной семантикой, способной стать именем не того элемента. Проверить фактическую озвучку в целевых браузерах.
- `nestedControls`: отдельная демонстрационная карточка с визуально вложенной структурой и интерактивным потомком (например, внешний `role="button"` и внутренняя кнопка). **Не** создавать `button` внутри `button` в основной ToDo: невалидная вложенность даёт непредсказуемую DOM-гидратацию и может сломать всё приложение.
- Отдельный показ «визуальная иерархия ≠ доступная иерархия»: текст рядом с иконкой не гарантирует корректное имя *соседней* кнопки.

**Проверить:** какой текст читает NVDA/VoiceOver/TalkBack, какие узлы реально появляются в Accessibility Tree, можно ли достичь вложенных элементов последовательной навигацией.

### BREAK-02. `flex-reverse` и порядок DOM

**Сценарий:** задачи выглядят сверху вниз в одном порядке, `Tab`/скринридер проходят их в обратном.

**Где:** `ChecklistCard.css`, при желании `TaskItem.css`.

```css
.demo-surface[data-reverse-order='true'] .checklist-card__task-list {
  display: flex;
  flex-direction: column-reverse;
}
```

**Важно:** `row-reverse` / `column-reverse` **не переставляют DOM**; это намеренное расхождение CSS-визуального и программного порядков. Если нужен именно *перемешанный DOM*, создать **отдельный** режим `reorderedDom`, в котором порядок элементов массива меняется детерминированно, а CSS возвращает визуальный порядок через `order`. Для минимального стенда достаточно первого варианта.

**Проверить:** экранное расположение, последовательность `Tab`, порядок элементов в браузерном Accessibility Tree и озвучивание скринридером.

### BREAK-03. «Невидимый фокус»

**Где:** отдельный `src/demo/demo-faults.css`, **не** глобальный reset всех `:focus-visible`.

```css
.demo-surface[data-no-focus-outline='true']
:is(button, a, input, textarea, select, [tabindex]):focus-visible {
  outline: none !important;
  box-shadow: none !important;
}
```

Gravity UI может показывать фокус через дополнительные псевдоэлементы/обводку — после внедрения проверить реальную картинку. Не подавлять фокус у **панели ведущего**, `Сброса` и `Остановить эффект`: панель находится **вне** `.demo-surface`.

**Проверить:** `document.activeElement` меняется при `Tab`, визуальный индикатор исчезает только на демонстрационной поверхности.

### BREAK-05. `alt` у изображений

**Условия:** в текущем ToDo преимущественно иконки Gravity UI как SVG; режим `alt` бессмысленен, пока не появится хотя бы одна **информативная** картинка (`<img>`), например визуальная инструкция, чеклист-карточка с изображением или мини-карта.

**Переключатель из трёх значений:**
- `original` — исходное значение `alt`.
- `empty` — `alt=""` для всех **информативных** изображений в demo-surface (они пропадают как информация для AT).
- `missing` — атрибут `alt` отсутствует (AT может попытаться прочитать имя файла; это **не то же самое**, что `alt=""`).

В React предпочтительно использовать контролируемый `<DemoImage>` вместо прямого изменения DOM после рендера. На inline-`<svg>` атрибут `alt` не действует: SVG обрабатывать отдельно через `role`, `aria-label`, `<title>` и/или `aria-hidden`.

**Критически важная оговорка:** пустой `alt` на **декоративной** картинке — нормальная практика, не ошибка. Демонстрируем потерю информации только на содержательных изображениях.

### MODAL-01 / MODAL-02. Фокус, scroll lock, конфликт autofocus

**Где:** `ChecklistModal.tsx`, `TaskModal.tsx`, отдельная демонстрационная оболочка `BrokenDemoDialog.tsx` при необходимости.

**Original (контроль):** модалка открыта; фокус переводится внутрь, `Tab`/`Shift+Tab` остаются внутри; фон недоступен для взаимодействия, прокрутка `body` заблокирована; `Escape` закрывает, фокус по возможности возвращается инициатору.

**Hard:** убрать **поведение**, а не только ARIA:
- нет focus trap;
- нет блокировки `body` scroll;
- фон остаётся интерактивным;
- после открытия возможно сохранение фокуса на кнопке за модалкой.

Gravity UI `Modal` может самостоятельно управлять trap/scroll. Сначала проверить наличие поддерживаемых пропсов. Если отдельных переключателей нет — не ломать библиотеку CSS-костылями: использовать отдельный простейший **демонстрационный** диалог, не подменяя обычный.

**Autofocus collision (отдельный тумблер):** поле в диалоге запрашивает `autoFocus`, но внешний элемент/эффект при открытии программно запрашивает фокус позже. Делать явно управляемый конфликт, иначе браузер и React StrictMode могут давать нестабильные исходы. `autoFocus` сам по себе не означает, что два элемента одновременно сфокусированы.

**Проверить:** активный элемент сразу после открытия, `Tab` 5–10 раз, `Shift+Tab`, скролл фона, Escape, возврат фокуса, работа экранной клавиатуры на телефоне.

### VISION-01. Color wheel / изменение CSS-цветов

**Разделить два разных эффекта:**
1. `paletteChaos` — произвольная, но **фиксированная** перестановка цветов дизайн-токенов/цветов категорий: демонстрация зависимости значения от одного лишь цвета.
2. `colorVisionPreset` — отдельные приблизительные фильтры/матрицы для протан-, дейтерано- или тритан-дефицитов. **Не** называть их симуляцией полной слепоты.

Реализация без тяжёлых зависимостей: поставить на `.demo-surface` data-атрибут для заранее определённой палитры и/или CSS/SVG color-matrix filter. Генерировать палитру случайно при каждом рендере **нельзя**: тесты и сравнение станут невоспроизводимыми.

Показывать это на задаче, где приоритет узнаётся преимущественно по цвету. Сохранять оригинальные текстовые значения, чтобы было видно, что является визуальной помехой, а что — отсутствием семантики.

### VISION-02. Частичная травматическая оптическая нейропатия (TON)

**Короткий иллюстративный пресет:** снижение контраста, выборочное приглушение цвета, мягкая условная скотома. Расположение дефекта — параметр демонстрации. Для одно- или двусторонних эффектов на мониторе точное соответствие субъективному зрению невозможно.

- Эффект накладывать на `.demo-surface`, **не** на управление стендом.
- Не считать экранную затемнённую область «так человек видит при TON»: реальные скотомы не обязаны восприниматься как серые пятна, и фиксированное пятно не следует направлению взгляда.
- Дать надпись: *«Иллюстрация некоторых зрительных нарушений, возможных при частичной TON; не медицинская симуляция»*.

### FX-01. CRT

Поверхность `::before`/`::after` со скан-линиями и слабым шумом, при желании лёгкая дисторсия; класс `.demo-surface[data-crt='true']`. **По умолчанию выключен.** Не делать интенсивного мерцания или вспышек; предусмотреть `prefers-reduced-motion`, ручной `Pause effects` и проверку производительности на телефоне.

CRT — эстетический барьер/перцептивный эффект, **не** симуляция конкретного диагноза и не основной a11y-сценарий.

### MEDIA-01. Анимация и «виртуальный фокус»

**Идея:** небольшая движущаяся карточка/индикатор, которая при взаимодействии перестаёт двигаться. При настоящем DOM-фокусе применить `:focus-within`/`focusin`, при мыши — `:hover`, а для всех — явное управление «Приостановить движение».

**Ограничение:** виртуальный курсор скринридера **не гарантирует** DOM `focus`. Нельзя обещать `pause on virtual focus` только через CSS/JS `focusin`. Если цель — проверить такое поведение, оформить как **экспериментальный кейс**, испытать на конкретных связках NVDA/VoiceOver/TalkBack, а ручную паузу сделать гарантированным выходом.

### EDITOR-01. «Грязный» Markdown-редактор

Необязательный отдельный экран с визуально удобным редактором описания задачи, но намеренно плохой семантикой: иконки без названий, переключение `Редактор/Предпросмотр` без объявления, отсутствие заголовков/списков в preview, конфликт фокуса на toolbar. Не использовать небезопасный raw HTML из ввода пользователя для `dangerouslySetInnerHTML`; если нужен Markdown render — санитайзить HTML или ограничить поддерживаемый синтаксис.

### MAP-01. Карта — кандидат на исключение

Если нужна демонстрация того, что карту трудно воспринимать без текстового эквивалента, лучше начать с **локального SVG/изображения** с 2–3 отмеченными точками и переключателем альтернативного описания. Полноценный MapLibre/тайлы/поиск маршрутов непропорциональны срокам стенда.

**Хостить все ресурсы локально относительно приложения:** картинка/данные карты, шрифты и дополнительные медиа в `public/` или в сборке Vite. Никаких вызовов публичного tile-server, geocoding API или CDN в runtime. Это **не** означает, что сайт откроется без сети: для телефона всё равно нужен адрес хоста Егора или LAN-сервер.

### Как это работает

```
main.tsx
└─ DemoProvider            ← фаза, кейс, формат, флаги, runId, время
   └─ (ключ runId)         ← пересоздание = полный сброс
      ├─ DemoBar           ← вне поверхности: режим, таймер, шаги, «Не получается», «Сбросить»
      └─ <main class="demo-surface" data-флаги>
         └─ экран кейса: ToDo (1Б, 2В, 2Б) | Регистрация (2А) | Корзина (1А)
```

- **Сброс** = `runId + 1`: всё под ключом пересоздаётся из seed кейса; модалки закрыты, карточки свёрнуты. Переход Hard → Original — тоже сброс.
- **Без localStorage:** перезагрузка страницы = аварийный сброс, следующий посетитель ничего не наследует.
- **Шаги и ошибки:** экран кейса сам считает `steps: boolean[]` и `mistakes: number` из своего состояния и передаёт в `useDemo()`. DemoBar знает только подписи из `cases.ts`.
- **Фазы:** задание (выбор кейса и формата, «Начать») → Hard → «Готово за 2:31, теперь без барьеров» → Original → итог (два времени, ошибки, «Что мешало» по включённым флагам) → «Сбросить».
- **«Не получается»** доступна всегда: фиксирует время как «не завершено» и переводит дальше. Подсказки по времени нет. Ничего не записывается и не отправляется.
- DemoBar работает с клавиатуры и скринридером в любом режиме, смена фазы и шаги объявляются через `aria-live="polite"`.
- **Без своего кода, средствами ОС:** штурман читает, что слышит ведомый, в VoiceOver Caption Panel (Mac) / NVDA Speech Viewer (Windows).

## 4.2. Квест «Ты — спикер» (16.11)

> Статус: **сделано 16.11**. Сравнение — весь квест с барьерами, затем весь без них. В отличие от черновика, сложный режим включает флаги **текущего дела**, а не объединение по квесту: иначе вложенность из «+1» снова прятала бы мерч. Отдельные кейсы — на лендинге в «Выбрать отдельное задание» и у ведущего.

### История и маршрут

Посетитель — **спикер, который едет на конференцию**. Чеклист квеста — его дела; каждый пункт — существующий кейс с новым заданием и подписями. Пункт отмечается сам, как сейчас шаги.

| # | Пункт чеклиста | Кейс | Что меняется в кейсе | Барьеры |
|---|---|---|---|---|
| 1 | Подать заявку на доклад | 2А | поля: имя, email, тема доклада, формат (доклад / воркшоп), согласие; пароли убраны | только placeholder, перемешанный `Tab`, автофокус на втором поле, «Условия» без ловушки |
| 2 | Вписать +1 | 1А | «Билет спикера» (бесплатно, 1 шт.), «Гость +1», «Афтерпати» (1 шт.); задание: добавить гостя, убрать афтерпати | карточка-кнопка, мусорный SVG, «удалить» — голый SVG |
| 3 | Заказать мерч (кружку) | Мерч | — | пустой alt |
| 4 | Добавить задачу «Проверить презентацию», критическую | Новая задача | — | модалка не держит фокус |
| 5 | Отметить свой доклад в 14:00 | 2В | «твой доклад» в расписании | обратный порядок, нет outline |
| 6 | Отметить «Отправить слайды организаторам» | 1Б | вместо «Позвонить спикеру» | чекбоксы без имён |
| 7 | Удалить «Черновик слайдов», чеклист оставить | 2Б | новое название задачи | фокус за модалкой |

Пункты 4–7 — один экран «Подготовка к докладу» с общими данными; между пунктами он не пересоздаётся.

- **Короткий квест (3–4 мин, по умолчанию):** 1 → 2 → 4 → 6 — форма, вложенность, модалка, имена.
- **Полный квест:** все 7 пунктов.
- **Новых пунктов не добавляем.** «Загрузить слайды» (поле файла без подписи) — кандидат в P1.

### Лендинг

- **Инструкция для своего устройства:** платформа определяется сама (Mac, Windows, iPhone, Android, без скринридера); её шаги видны сразу, остальные — в «Другие устройства». Включить и выключить скринридер, перейти к следующему элементу, нажать, прокрутить.

Вместо экрана выбора задания — **лендинг квеста**:
- заголовок «Квест: ты — спикер конференции», 2–3 строки истории и что будет: сначала с барьерами, потом без;
- выбор формата: Сам / Сам, пустой экран / В паре (как сейчас);
- главная кнопка **«Начать квест»** — короткий маршрут;
- ниже отдельным пунктом **«Выбрать отдельное задание»** (раскрывающийся блок): список кейсов, как сейчас; полный квест — тоже здесь;
- выбора задач в основном пути нет.

### Переходы между пунктами

- Пункт выполнен → экран кейса сменяется **карточкой успеха**: «Заявка подана! 0:42» и кнопка **«Дальше: Вписать +1»**. Фокус — на заголовок карточки, скринридер сразу его прочитает.
- Автоперехода нет: посетитель со скринридером должен успеть дослушать.
- Пункт с ошибкой (удалил весь чеклист, лишнее в заказе) — та же карточка, но «Готово, ошибок: 1».
- **«Пропустить»** у каждого пункта вместо одного «Не получается» → карточка «Пропущено» и «Дальше».
- В панели — чеклист квеста: выполненные, текущий, оставшиеся.
- После последнего пункта — карточка «Квест пройден за 3:12» и переход к сравнению (см. вопрос).

## 5. Тестирование: desktop + mobile (обязательный этап, не «посмотрели в DevTools»)

### 5.1. Автоматизация Playwright

Добавить проекты с эмуляцией мобильных устройств; это **проверка layout/touch/маршрутов**, не проверка реального VoiceOver/TalkBack:

```ts
projects: [
  { name: 'desktop-chromium', use: { ...devices['Desktop Chrome'] } },
  { name: 'android-emulation', use: { ...devices['Pixel 7'] } },
  { name: 'iphone-emulation', use: { ...devices['iPhone 13'] } },
]
```

Проверить, что установлены необходимые браузеры Playwright (мобильная эмуляция iPhone обычно использует WebKit). Если не установлены, поставить их в подготовленной среде до демонстрации. Не изменять `webServer` на внешний хост: E2E достаточно локального Vite, а ручные испытания проходят по адресу Егора.

**Новые E2E (`e2e/demo.spec.ts`, `e2e/demo-mobile.spec.ts`):**
- `[ ]` Сброс возвращает исходные seed-данные и закрывает модалки.
- `[ ]` Hard → Original не оставляет включённые CSS-фильтры/скрытые кнопки.
- `[ ]` `reverseVisualOrder`: фактический DOM/Tab-order и экранный порядок различаются **как задумано**.
- `[ ]` `hideFocusOutline`: outline отключён только внутри поверхности.
- `[ ]` `emptyImageAlts`: только информативная `<img>` теряет доступный текст; после отключения возвращается.
- `[ ]` Hard-модалка позволяет уйти фокусом в фон, Original-модалка не позволяет (если поддерживает выбранная реализация).
- `[ ]` Не возникает горизонтального скролла и перекрытия элементов управления на **320, 360, 390, 430 px** в стандартном режиме; намеренные дефекты тестируются отдельно.
- `[ ]` Тапы по кнопкам, открытие модалки, ввод с экранной клавиатурой, закрытие, сброс.
- `[ ]` Таймер устойчив при обновлении экрана/смене вкладки (явно определить: продолжает считать wall-clock или паузится); без runaway interval.
- `[ ]` На выбранных устройствах нет ошибок JS, зависаний или заметной деградации от фильтров.

**Важно:** намеренно недоступный Hard **не должен** проходить общий набор a11y-assertions как доступный. Проверяются заданные нарушения и отсутствие неожиданных технических отказов. Не принимать «прошли E2E» за доказательство поддержки скринридеров.

| Среда | Что проверить | Минимальный критерий |
|---|---|---|
